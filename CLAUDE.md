# Wh Generation Forecast

Forecasts the hourly energy (Wh) generated by a solar panel feeding an EcoFlow Delta 2 at Vibora Park, Havana. Python 3.13, managed with `uv`.

## Layout

```
src/wh_forecast/   data/ (Open-Meteo clients, scrapers)  features/  models/  api/  config.py
scripts/           thin entry points (fetch data, train)
notebooks/         exploration only; no logic that the package needs
tests/             pytest (tests/unit, tests/integration)
data/              raw and processed data, trained models (git-ignored)
docs/ openspec/    documentation and specs
```

Commands: `uv sync --extra dev`, `uv run pytest`, `uv run python scripts/train_solar_model.py`.

## Code conventions

- Type hints on all function parameters and return values.
- Document the flow in the docstring (Google style). Comment only to explain why, never to restate what.
- No numbered step-by-step inline comments such as `# 1. Load`.
- Build features in one module (`features/`) that training and prediction both use.
- Split time series chronologically; never shuffle.

## Development Workflow: OpenSpec + Superpowers

**OpenSpec owns all planning and specs** (proposal, design, specs, tasks) under `openspec/`. Do not write specs or plans elsewhere (no `docs/superpowers/`).
**Superpowers is used only while applying a change**, for how the code is written and checked.

| Phase | Tool |
|-------|------|
| Explore | `/opsx:explore` |
| Plan / specs | `/opsx:propose "idea"`, `/opsx:update` |
| Implement | `/opsx:apply`, using `superpowers:test-driven-development` for every task |
| Verify | `superpowers:verification-before-completion`, then `/opsx:verify` (if enabled) |
| Review | `superpowers:requesting-code-review` |
| Finish | `/opsx:sync`, `/opsx:archive` |

Rules:
- Every feature or behavior change starts as an OpenSpec change.
- During apply, write the failing test first, then the code (TDD).
- Check off a task in `tasks.md` only after verification commands pass, with evidence.
- Request code review and verify before archiving.
- If implementation diverges from the specs, update the change with `/opsx:update`; do not leave specs stale.
- Trivial fixes (typos, config tweaks) may skip OpenSpec but still follow TDD and verification.
